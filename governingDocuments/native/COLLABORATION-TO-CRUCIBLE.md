# Collaboration to Crucible Integration Specification

## Purpose

This document defines the governed interaction between `AI-collaboration-` and `The-Crucible`.

The collaboration layer may generate proposed coding actions, reasoning, evidence references, and candidate solutions.

The Crucible independently evaluates those outputs.

Agreement by AI models, council members, providers, or collaboration processes does not constitute Crucible verification.

This integration does not transfer verification authority, governance authority, or custody authority.

---

# Integration Overview

Source Repository:

- AI-collaboration-

Destination Repository:

- The-Crucible

Purpose:

- Submit proposed coding actions
- Submit generated artifacts for checking
- Submit reasoning and supporting evidence
- Request verification
- Receive verification results
- Receive failure information and remediation requirements

---

# Ownership Boundaries

## AI-collaboration- Owns

- Collaboration execution
- Model/provider coordination
- Council execution
- Reasoning aggregation
- Candidate solution generation
- Collaboration provenance

## The-Crucible Owns

- Coding verification
- Evidence assessment
- Verification checks
- Failure classification
- Scientific validation where applicable
- Crucible verification status
- Verification evidence

# Crucible Evaluation

Upon receiving a valid `VerificationRequest`, The-Crucible independently determines the applicable checks.

The Crucible may:

- Accept the request for evaluation
- Reject an invalid request
- Execute verification checks
- Identify failures
- Request additional evidence
- Produce a verification result
- Produce a remediation requirement
- Produce an inconclusive result

The collaboration layer cannot alter the Crucible result.

# Verification Outcomes

The integration recognizes the following outcomes:

- PENDING
- INCONCLUSIVE
- VERIFIED
- REJECTED
- FAILED
- SUPERSEDED

A collaboration result must not be represented as `VERIFIED` until a corresponding Crucible verification result establishes that state.

---

# Evidence Requirements

Every verification request must preserve:

- Source references
- Proposal references
- Repository state
- Evidence references
- Provenance
- Lineage

Missing or incomplete evidence must not be silently converted into a successful verification state.

---

# Failure Handling

If Crucible identifies a failure:

1. The failure is recorded.
2. The failure retains its Crucible classification.
3. The failure remains linked to the originating request.
4. The collaboration layer may generate remediation.
5. Remediation must be resubmitted for verification.
6. The original failure record is not erased by remediation.

---

# Re-Verification

A remediation or modified proposal constitutes a new verification activity or a new version of the existing verification workflow as determined by Crucible governance.

The new activity must preserve ancestry to the original request and failure
